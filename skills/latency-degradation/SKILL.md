# latency-degradation

延迟升高故障域排查 SOP：适用于 P99/P95 延迟飙升、接口变慢、慢查询、连接池耗尽、LatencySpike 等告警。

## 适用告警特征

- 告警标题/标签含 latency、延迟、P99、P95、slow、慢查询、connection pool、timeout、LatencySpike
- 现象：接口响应时间明显上升、用户感知变慢、依赖调用超时

## 取证顺序

1. **检索历史**：先 search_incident_kb 用「服务名 + 延迟/慢查询」查相似事故。
2. **确认延迟画像**：按服务/接口/状态码看延迟分布（如 Prometheus `histogram_quantile` 的 p99/p95、avg），确认是整体变慢还是个别接口/路径。
3. **查依赖链路**：延迟常由下游引起。用 spawn_agent 并行检查上游/下游服务延迟、依赖（DB/ES/缓存/第三方）的响应时间，判断是否级联。
4. **看慢查询/慢日志**：用 tail_logs 查应用日志中的慢查询、超时、重试记录；有 DB/ES 慢日志源时优先看。
5. **查连接与队列**：检查连接池使用率/排队长度（连接数 vs max）、消息队列堆积量、线程池排队。
6. **看资源竞争**：CPU 使用率、GC 停顿、限流/背压迹象（如容器 CPU throttle、限流日志）。

## 典型根因模式与判断依据

- **连接池耗尽**：连接数饱和、请求在获取连接处排队，日志出现"waiting for connection / timeout acquiring"。判断依据：连接使用率接近上限且与延迟曲线同步。
- **慢 SQL / 慢查询**：慢日志集中在特定查询，延迟与该查询执行时间强相关；常见缺索引、全表扫描、锁等待。
- **下游依赖延迟**：本服务延迟随依赖延迟同步上升，且无本地异常；典型为级联超时、重试放大。
- **GC/CPU 竞争**：CPU 持续高位、GC 频繁，延迟呈周期性抖动；结合线程转储判断。
- **队列堆积**：消息/任务积压导致处理延迟；队列深度与延迟正相关。

## 易踩坑点

- 先分清"整体变慢"还是"个别接口变慢"——前者更像资源/依赖问题，后者更像代码/慢查询问题，方向不同。
- 超时配置过短导致的"快速失败"可能掩盖真实延迟，注意区分错误率与延迟两类信号。
- 级联故障时不要只查本服务，务必看依赖侧指标再下结论。
- mock/离线环境若指标不全，用日志时间线与错误分布交叉验证。
