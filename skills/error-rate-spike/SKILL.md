# error-rate-spike

错误率/5xx 飙升故障域排查 SOP：适用于 5xx 比例上升、错误率告警、ErrorRate、status>=500 等告警。

## 适用告警特征

- 告警标题/标签含 5xx、error rate、错误率、ErrorRate、HTTP 500、异常率
- 现象：接口错误率明显上升、部分请求失败、客户端报错增多

## 取证顺序

1. **检索历史**：先 search_incident_kb 用「服务名 + 5xx/错误率」查相似事故。
2. **确认错误画像**：按服务/接口/状态码聚合错误率（如 Prometheus `sum(rate(http_requests_total{status=~"5.."}))`），确认是全部接口还是个别接口、集中在哪个状态码（500/502/503/504 含义不同）。
3. **看依赖健康**：5xx 常来自下游。用 spawn_agent 并行检查依赖服务状态、数据库/缓存/上游 API 是否异常。
4. **看错误日志**：用 tail_logs 查应用日志中的异常堆栈/错误关键字，定位代码层面的报错点（空指针、未捕获异常、连接失败）。
5. **看 Pod 健康**：`kubectl get pods -n <ns>` 检查是否有个别 Pod 异常（OOM、探针失败、资源不足被驱逐），错误可能只来自部分副本。
6. **关联变更**：回看近期部署、配置变更、流量突增时间点，错误率上升常与变更/发版相关。

## 典型根因模式与判断依据

- **下游故障**：错误集中在 502/503（网关/上游不可达、上游超时），依赖侧指标异常。判断依据：下游服务错误率同步上升。
- **代码异常**：错误集中在 500，日志有明确异常堆栈（空指针、数据格式错误、第三方 SDK 失败）。判断依据：堆栈集中在特定代码路径。
- **限流/熔断触发**：503 大量出现，命中限流阈值或熔断规则；伴随 QPS 突增。判断依据：错误时间点与 QPS 尖峰重合、有 RateLimit/CircuitBreaker 日志。
- **配置/发版问题**：错误率上升时间点与发版/配置变更重合，回滚或修正配置后恢复。
- **部分副本异常**：仅个别 Pod 错误率高（如该副本内存/连接异常），整体错误率由少数坏副本贡献。

## 易踩坑点

- 先按状态码分桶再下结论——500（代码）、502/504（网关/上游）、503（限流/容量）指向完全不同的问题。
- 区分"错误率上升"与"流量上升带来错误数上升"——用 rate/比例而非绝对计数。
- 只读诊断时用 kubectl get/describe/logs 与 curl GET，不做回滚/重启等写操作，给出建议等待审批。
- mock/离线环境错误日志不足时，用指标中的状态码分布 + 时间关联推断。
