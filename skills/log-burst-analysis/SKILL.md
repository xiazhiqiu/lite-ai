# log-burst-analysis

日志风暴/异常日志排查 SOP：适用于日志量激增、ERROR 刷屏、日志增长异常、日志格式异常等告警。

## 适用告警特征

- 告警标题/标签含 log burst、日志量、日志风暴、log flood、ERROR 刷屏、异常日志
- 现象：单服务日志量短时间内激增、日志中出现大量重复错误/堆栈、日志增长速率异常

## 取证顺序

1. **检索历史**：先 search_incident_kb 用「服务名 + 日志/报错」查相似事故。
2. **确认日志量与形态**：用 tail_logs 先看末尾 N 行，判断是"大量重复同类错误"还是"多种异常混杂"；必要时用 follow_logs 观察日志演进趋势。
3. **统计错误分布**：对日志做关键字/错误码聚合（如 grep ERROR/Exception/特定错误码后计数），找出占比最高的异常类型——日志风暴通常由单点异常放大。
4. **定位触发源**：抓取代表性错误行（含堆栈的完整片段），判断是业务循环报错、重试风暴、还是崩溃转储。
5. **时间关联**：确认日志激增的起始时间点，与部署、配置变更、流量事件交叉比对。
6. **追根因链路**：若为重试风暴，回溯到触发方（依赖不可用、认证失败、配置缺失导致反复重试）；若为崩溃转储，结合 OOM/进程退出检查。

## 典型根因模式与判断依据

- **重试风暴**：日志中同一错误以固定间隔反复出现，且量随依赖故障放大；常见连接失败、认证失败、超时重试。判断依据：错误唯一标识多但错误类型单一、呈周期性。
- **循环业务报错**：特定输入反复触发同一异常（如脏数据、非法请求刷屏），错误随特定请求特征聚类。
- **日志级别误配/无界打印**：INFO/DEBUG 刷屏或大对象被反复打印，量级大但错误占比低。判断依据：日志量大但 ERROR 占比低、无异常堆栈。
- **崩溃转储/异常堆栈刷屏**：伴随进程反复重启，堆栈类型单一且与 OOM/启动失败相关。

## 易踩坑点

- 先"聚合分类"再"逐条看"：日志风暴逐条读会淹没重点，先用关键字/错误码统计找出主异常。
- 大文件用 tail_logs 的尾部读取（有 10MB 上限保护），需要持续观察时用 follow_logs 增量拉取而非反复 tail 全量。
- "日志多"不等于"故障严重"——区分 ERROR 刷屏（可能仅一条错误被高并发放大）与多类型异常并存（更可能系统性故障）。
- mock/离线环境日志源有限时，结合指标（错误率、QPS）与时间线交叉验证风暴来源。
